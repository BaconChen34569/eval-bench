## 二、你的作品是什么

**一句话**：一个面向课程项目的代码问答 Agent，加上一套能量化它"在哪错、错多少"的评测台——而且这套评测台自己也按同样的规矩被迭代了七轮。

在线体验：https://copilot-eval-bench-fzlro45ljfz.qoder.zone

它分两层，各自解决一个不同的问题：

### 1. 检索层（离线、确定性、可复现）

代码问答的质量上限由"检索到没检索到正确的代码"决定。这一层不调用任何大模型，只做：把仓库切成 chunk → 建 BM25 索引 → 检索 → 用人工标注的证据位置算 `evidence recall@K` 和 `MRR`。

**这一层的结果每次跑完全一样**，所以它能干净地隔离出一个变量：**切分策略**。我对比了三种切法：

- `fixed-800`：固定 800 字符窗口，切得快，但会把一个函数拦腰截断
- `fixed-400`：固定 400 字符窗口，上下文最省，但截断更碎
- `function-level`：按函数边界切，语义完整，但短函数会被切碎、长函数又可能超窗

结论直接写在站点上：**函数级切分把 recall@1 从 18.2% 提到 32.6%、MRR 从 0.445 提到 0.617**，正确代码块被排到了更靠前的位置；代价是每次要送 20,298 字符进 prompt，是固定 800 字符策略的 4.0 倍。切得更准，但每次问一次也更贵。

### 2. 生成层（LLM-as-judge，带自检）

检索对了之后，Agent 生成的答案对不对，用 `LLM-as-judge` 按 1–5 分打分（≥4 分算成功），并对每道题记录：引用的证据位置、延迟、token 消耗、实际花费。

**但 judge 自己如果不准，这套分数就是废的。** 所以在评测任何 Agent 之前，我先做了一次 **judge 自检**：让 judge 去给*人工写的参考答案*打分，再和这份参考答案的人工评分对比。

- 一致率：**100.0%**（20 题）
- judge 均分 **5.00** vs 人工均分 **4.40**（完全同分率 40.0%）

这组数字很关键，也有点出人意料：judge 在人工答案上打得比人工还高，说明它**偏宽松**。所以生成层的分数只能横向比较，不能当绝对质量看——这一点我把它明明白白写在了站点上，而不是藏起来。

三种切分策略跑同一批题（模型 deepseek-flash，同一份题、同一套检索）：

| 切分策略 | 成功率 | 平均 judge 分 | 平均 / P95 延迟 | 单题成本 | 总 token |
|---|---|---|---|---|---|
| 固定窗口 800 | 22.7% | 2.59 | 12.3s / 20.5s | ¥0.0166 | 166,174 |
| 固定窗口 400 | 22.7% | 2.55 | 11.6s / 16.4s | ¥0.0139 | 130,111 |
| **函数级切分** | **59.1%** | **3.77** | 13.3s / 25.4s | ¥0.0232 | 317,989 |

函数级切分的成功率是固定窗口 400 字符的 **2.6 倍**，代价写在同一行里：P95 延迟多了 55%，token 多用了 144%。精度换成本——这就是评测台存在的意义。

### 3. 失败归因

失败类型不是听 judge 自己说的，是按 ground truth 判的：先看有没有引用到仓库里根本不存在的位置（编造内容），再看检索有没有命中人工标注的证据——一条都没命中就是**定位错了**，说明瓶颈在检索侧；命中了但分数不够，才算**要点漏了**，说明该改的是提示词和模型。

| 切分策略 | 定位错了 | 要点漏了 |
|---|---|---|
| 固定窗口 800 | 6 题 | 11 题 |
| 固定窗口 400 | 7 题 | 10 题 |
| 函数级切分 | 3 题 | 6 题 |

最有价值的一条结论在这儿：**函数级切分的 9 次失败里只有 3 次是定位错了（33%），另外 6 次是检索到了却没把要点答全**——也就是说它的瓶颈已经从"检索"挪到了"生成"，下一步该改提示词和模型，而不是继续换切法。这句话不是我猜的，是失败归因算出来的。

### 4. 工具迭代阶梯（把评测台自己当被测对象）

上面三节评的是"课设 Copilot 这个 Agent"。这一节评的是**评测台本身**：我是怎么一步步把这个工具改好的。

协议是死的：同样 22 道题、同一个模型（deepseek-flash）、同一套 judge、同样 ≥4 分的成功线，**每一轮只相对上一轮改一个变量**，然后整套重跑。

| 轮次 | 这一轮改了什么 | 成功率 | judge 均分 | 检索召回@预算 | 上下文 | 成本 |
|---|---|---|---|---|---|---|
| v1 | 起点：固定窗口 800 字符 + 纯 BM25 top-6 + 基准提示词 | 22.7% | 2.41 | 47.7% | 5,044 | ¥0.3082 |
| v2 | 只改切分：固定窗口 → 函数级切分 | 31.8% | 3.09 | 49.2% | 12,161 | ¥0.3985 |
| v3 | 只改排序：纯 BM25 → BM25 + 符号名加权 | 45.5% | 3.23 | 53.8% | 11,033 | ¥0.3894 |
| v4 | 只改提示词：先列依据位置，再据此作答 | 36.4% | 3.00 | 53.8% | 11,033 | ¥0.3766 |
| v5 | 只改预算：top-6 → top-10 | 54.5% | 3.45 | 62.1% | 17,953 | ¥0.4459 |
| v6 | 只改查询：中文术语展开成英文候选词 | 59.1% | 3.95 | 78.8% | 34,317 | ¥0.7067 |
| **v7** | 只改重排：符号加权 → 结构感知（路径单独加权） | **72.7%** | **4.00** | **81.1%** | 40,949 | ¥0.7163 |

这个阶梯能读出四件排行榜读不出来的事：

1. **收益来自哪一层。** 换切分贡献 +9.1 个百分点，加符号名重排 +13.6 个点，放宽检索预算 +18.2 个点，补中英术语桥 +4.5 个点，改成结构感知重排 +13.6 个点——每一笔都归到了具体的一个改动上。
2. **检索涨了，生成有没有跟着涨。** 检索层的证据召回率是**离线算的，不调用任何模型，所以完全免费、任何人几分钟就能重算一遍**。它从 v1 的 47.7% 一路涨到 v7 的 81.1%，生成层同轮从 22.7% 涨到 72.7%——这条因果链对上了，说明这些改动是真的起作用，不是运气。
3. **一轮中文提问救回一批题。** v6 只改了一件事：把中文问题里的术语展开成英文候选词一起参与打分。因为题干是中文、代码是英文，字面上一个词都对不上，那一轮召回直接从 62.1% 跳到 78.8%。这是全阶梯里最便宜的一次改动——只动查询构造，不动模型、不动提示词。
4. **哪些改动没白花钱，以及哪一轮单独看是亏的。** v4（改提示词）单独看把成功率从 45.5% 拉低到 36.4%，而那一轮检索层的召回一点没变（53.8%），说明掉分的是提示词本身；但这个改动被后面三轮一路继承，最后一轮做到了 72.7%。**一个单独看是负收益的改动，把它从曲线里抹掉，就没法知道后面的收益有多少来自它。**

另外，22 道题里有 13 道是在某一轮被修好的（其中 4 道在换切分方式那一轮就修好了），5 道一开始就能答对，剩下 4 道到最后一轮仍然没答对——阶梯暴露出"改不动的地方"：这些题不是被某一次改动修好的，而是检索根本捞不回证据，或者推理链缺了关键一步。

### 5. 优化前后：评测台自己也升级了一版

前面几节评的是 Agent，但评测台自己也是一件软件，它也会用错方法。所以我把**上一版评测台跑出来的记录原样搬过来**（不是手写数字），和当前版本逐题对照——同一批题、同一个模型、同一把 judge 尺子、同一 ≥4 分的成功线。

| 指标 | 上一版（r2） | 当前版（r3） | 变化 |
|---|---|---|---|
| 成功率 | 31.8% | **59.1%** | +27.3 个百分点 |
| judge 均分 | 2.91 | **3.77** | +0.86 |
| 证据召回率（top-6） | 45.5% | **69.7%** | +24.2 个百分点 |
| MRR | 0.447 | **0.617** | +0.170 |
| 平均上下文（字符） | 11,743 | 20,298 | 多了 73% |
| 切出的代码块数 | 730 | **557** | 少了 173 块 |

这一版一共改了四处代码（站点上原样列着）：

- 切分：多行 `def` 签名不再被吞掉，函数块重新带上完整签名
- 切分：类内部的空隙不再单独成块，块数从 730 降到 557
- 检索：重排从符号加权升级为结构感知，文件路径单独加权
- 检索：新增中英术语扩展，中文提问也能命中英文代码

逐题看：**11 道题分数变高（其中 6 道从不及格变成及格），1 道题变低，9 道题到当前版本仍然没答对。**

最反直觉的一条是"块数少了、成功率反而涨了"：上一版把类内部那些没意义的空隙也单独切成了块，这些块对任何一道题都没用，只是在稀释检索结果；这一版不再切它们，块数少了 173 块，检索质量反而上去了。

## 三、为什么做

因为**现在大部分人做 AI Agent，展示的都是"它能做什么"，几乎没人展示"它在哪里不行"。**

我自己被这个问题坑过。用 AI 助手读代码的时候，我没有办法验证它，只能选择相信或者不信——这不是工程做法，是运气。

我想做的是把"相信"变成"有依据"：

1. **把主观变客观**。"这个回答看起来挺靠谱"没法写进报告，"在 22 道人工标注题上成功率 X%，P95 延迟 Yms，单题成本 Z 元"可以。
2. **把失败变成可定位的**。不只是"错了"，而是"因为切分把 `wsgi_app` 截断了所以定位错了"。能定位才能改。
3. **把 judge 的可信度也纳入验证**。这是最容易被跳过的一步——评测工具自己如果不准，整个体系就是空中楼阁。
4. **把评测台自己也当被测对象**。定位到了失败，不等于改完了。我用一套"每轮只改一个变量、其余全部锁死"的阶梯协议重跑了七轮，把每一笔收益都归因到具体改动上——包括**没赚回来的那一轮**。评测台本身也留了一份上一版的运行记录，改完代码重跑一遍就能看出自己到底进步了多少（31.8% → 59.1%）。

场景选在**课程项目**上，是因为这是我最有真实感的场景：我是这些仓库的第一批用户，我知道自己哪里会问错，也能拿到真实的失败样本，不需要去想象一个虚构用户。

## 四、怎么用（5 步以内）

在线体验版：打开站点 → 看三种切分策略的检索对比 → 点开任意一道题看逐题检索台（同时能看到三种策略在这道题上的并排对比）→ 看失败归因 → 看 judge 自检结果 → 看「优化前后」这一节的上一版对照 → 看「工具迭代史」这一节的七轮阶梯 →（想自己抠数字的话）切到「数据」视图逐题筛选，或直接把 CSV / JSON 下载走。

**想要代码的话：整个项目都开在 GitHub 上** —— https://github.com/BaconChen34569/eval-bench ，MIT 许可。里面是完整的评测流水线、22 题评测集、语料拉取脚本和站点源码。**不需要注册、不需要账号、不需要 API 密钥**，装个 Node.js 22.13 以上就能跑出和站点一模一样的检索层数字（检索层完全离线、不花钱）。

如果你想在自己身上跑一遍：

```bash
# 0. 拿到代码
git clone https://github.com/BaconChen34569/eval-bench.git && cd eval-bench

# 1. 拿到被测仓库（这里以 Flask 3.1.3 为例）
bash corpus/fetch.sh

# 2. 配置模型密钥（DeepSeek，OpenAI 兼容接口）
cp harness/.env.example harness/.env && 编辑 harness/.env

# 3. 一条命令跑完整套评测：检索层 + judge 自检 + 生成层
cd harness
node --experimental-strip-types src/cli.ts experiment \
  datasets/flask.json ../corpus/repos/flask-3.1.3 --out out/report.json

# 4. 再跑七轮迭代阶梯（每轮只改一个变量）
#    --reuse 会复用配置一致、且代码版本一致的已有运行记录
node --experimental-strip-types src/cli.ts ladder \
  datasets/flask.json ../corpus/repos/flask-3.1.3 --out out/report.json --reuse out/report.json

# 5. 想看"优化前后"：把旧报告作为基线传进去，两版逐题对照
node --experimental-strip-types src/cli.ts ladder \
  datasets/flask.json ../corpus/repos/flask-3.1.3 --out out/report.json \
  --baseline out/report-old.json

# 6. 把生成的报告灌进站点
cp out/report.json ../site/data/report.json

# 7. 本地看
cd ../site && npm run dev
```

换成**你自己的课设仓库**只需要改两处：`datasets/` 里换一份带人工标注证据的题集，`corpus/repos/` 里放你的仓库路径，其余一行不用动。

**① 设计工作台**：先把站点的信息结构和视觉方向定下来

**② 实现评测流水线**：从数据契约（schema）开始，再逐个模块往上搭
> 截图：`harness/src/` 下的实现过程（schema → chunk → retrieval → agent → judge → runner）

**③ 用 Qoder 排错**：这一段写两个真实的坑，都是这次做的时候真踩到并定位到的：
> - **成本口径算错了两次。** 第一版只统计了 agent 的 token，没算 judge 打分那一次调用；第二版把缓存命中的输入按未命中价计费。两次都是靠把账单口径和 API 返回的 `prompt_cache_hit_tokens` 对上才发现的——后来把成本折算改成独立模块，才算站得住。
> - **失败归因一开始是废的。** 原本让 judge 自己说错在哪，结果所有失败都落进"要点漏了"一档。改成用 ground truth 判：先查有没有引用到仓库里不存在的位置，再查检索有没有命中人工标注的证据，最后才归为漏要点。同一批数据重算之后，分布立刻有了意义——也直接指出了下一步该优化检索而不是提示词。

**④ 让评测台自己接受检验**：把上面那套阶梯协议真跑起来之后，抓到第三个坑——
> - **一次网络抖动把结论带偏了。** 早期版本的一次重跑里，有一轮成功率突然掉回上一轮的水平，第一反应是"这次改动有害"。但失败原因全是 `fetch failed`——网络断了，不是模型答错，而且一串题连着失败，明显是那一段时间的服务抖动。**如果只看成功率，我就会把这个假结论写进报告。** 我给 LLM 调用加了瞬时故障重试（只对网络错误、429、5xx 重试，生成超时仍然算失败，因为那是被测量的结果），重跑了那一轮，才拿到真实的数字。
>   这一步本身就是这个项目想说的事：**评测工具最危险的失败模式，是把基础设施故障当成被测对象的缺点。**

**⑤ 读失败样本，读出真正的瓶颈**：这一段是这次收获最大的一步——
> - 我把每一道失败的题目打开逐个看，发现有 6 道题**一条人工标注的证据都没命中**。第一反应是"切分把代码切碎了"，但把命中的 chunk 和题干并排放在一起看才发现不是这么回事：**题干是我写的中文，代码是 Flask 的英文源码，BM25 一个共同的词都匹配不上**。切分再怎么改也救不了这种题——检索器根本不知道该找什么。
> - 解法不是给这 6 道题打补丁（那样评测就废了），而是加一层**通用的中英术语桥**：把问题里出现的中文技术词展开成英文候选词，一起参与打分。通用词表 + 0.4 的权重，不针对任何一道题。这一轮（v6）召回从 62.1% 跳到 78.8%，是全阶梯里最便宜的一次改动——只动查询构造，不动模型、不动提示词。
> - 同一批失败样本还暴露了切分的两个 bug：多行 `def` 签名被吞掉（函数块丢了签名，检索到的片段没法判断它是什么函数），以及类内部的空隙被单独切成了块（这些块对任何题都没用，只是在稀释检索结果）。修完之后块数从 730 降到 557，成功率反而涨了。

**⑥ 把"优化前后"也变成数据**：上一版的运行记录我是留着的，所以这一版改进有多少不是靠感觉说——
> - harness 里加了 `--baseline`：把旧报告传进去，它会从旧报告里挑出最好的一次横向对比记录，跟当前版本**逐题对齐**，算出成功率、judge 均分、证据召回率、MRR、上下文、块数六项的变化，并逐题标出"哪几道被修好了、哪一道退步了"。
> - 结论：成功率 **31.8% → 59.1%**，其中 11 道题分数变高、6 道从不及格变及格、1 道变低。这个数字是脚本算出来再渲染到页面上的，**没有一个是我手填的**——这一点我特意检查过，因为手填的对照表最容易骗自己。
